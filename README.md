# package:lepic

## TL;DR

Dart bindings for the LEPIC wallet engine, generated by flutter_rust_bridge 2.13.0 from
`crates/lepic-ffi`. The app creates one `LepicRuntime`, gives each wallet an `AppSecretStore`
over its secure storage, and calls `EpicWallet` methods, which return Futures and Streams. Every
failure is a thrown `WalletError` with a stable numeric code. Only secrets the user types or
configures enter Rust, only the recovery phrase leaves it for Dart after a credential check, and
the PIN key leaves it only for the app's secret store (ADR 0014, below).
The package bundles the Android, iOS and Linux libraries through its build hook (below).

## Use

```dart
import 'package:lepic/lepic.dart';

await RustLib.init();
final runtime = LepicRuntime(logLevel: LogLevel.info);
runtime.logs().listen((entry) => debugPrint('${entry.level} ${entry.message}'));

final store = lepicSecretStore(myFlutterSecureStorageAdapter); // implements SecretStore
final wallet = await EpicWallet.create(
  runtime: runtime,
  config: WalletConfig(
    dataDir: dir.path,
    chain: Chain.mainnet,
    nodeUrl: 'https://node.example:3413',
    epicboxDomain: 'epicbox.epiccash.com',
    epicboxPort: 443,
  ),
  store: store,
  password: password,
);
```

- A password set by `EpicWallet.create` or `EpicWallet.importWalletSeed` has at least eight
  characters, or the call fails with `invalidArgument` before anything is written. `open` and
  `mnemonic` take any password that opens the vault, so a wallet with a shorter password keeps
  working. Their attempts are counted in the store as `lepic.pin-failures` and wait exactly as
  PIN attempts do (below); a right password clears the count.
- `SecretStore` has the same three methods as the app's `secret_store.dart` interface, so the
  app's `PlatformSecretStore` can be passed to `lepicSecretStore` unchanged. LEPIC writes
  `lepic.vault`: the seed encrypted under the wallet password (Argon2id, XChaCha20-Poly1305), and
  `lepic.pin-failures` after a failed password or PIN attempt, and `lepic.vault-next` while
  `changePassword` runs (below). A PIN wallet adds `lepic.pin-key`
  and, while a PIN change is pending, `lepic.pin-key-pending` (below). Store `lepic.pin-key-pending` exactly as `lepic.pin-key`, in
  the same keystore-backed storage: it is a PIN key too.
- Use one store per wallet, for example by prefixing keys with a wallet id in the adapter. The
  keys above have fixed names, so wallets sharing a store would share one vault slot, one PIN key
  and one failure count: a second wallet is refused with `walletAlreadyExists`, and wrong PINs
  for one wallet would delay attempts for another.
- For PIN unlock use `EpicWallet.createWithPin` and `EpicWallet.openWithPin`: LEPIC generates the
  wallet password, seals it under the PIN together with a random key it writes into the store as
  `lepic.pin-key`, and returns only the sealed text, which the app stores. A new PIN, in
  `createWithPin`, `importWalletSeedWithPin` and `changePin`, has at least six characters; a
  shorter PIN set by an earlier version still opens its sealed text. Every attempt is counted in the store as `lepic.pin-failures`. The first three
  attempts never wait; after the third failure each attempt first waits 30 s, twice as long after
  each further failure, up to an hour. A right PIN clears the count.
- Store the sealed text before showing the recovery phrase or receiving funds. If the app stops
  between `createWithPin` and storing it, the wallet cannot be opened by PIN: delete it with
  `deleteWallet` and create it again.
- `EpicWallet.changePin(sealedPassword, oldPin, newPin)` returns new sealed text for the same
  wallet password under the new PIN and a new PIN key, which LEPIC keeps as
  `lepic.pin-key-pending` beside `lepic.pin-key`. The old PIN attempt is counted and delayed like
  any other. The change is two-phase:
  1. Call `changePin` and keep the old sealed text.
  2. Store the new sealed text in place of the old one.
  3. Call `confirmPinChange(sealedPassword)` with the text the app now holds. Only now does the
     old sealed text stop opening.

  Until step 3 both pairs open, the old PIN with the old text and the new PIN with the new text,
  also after the app restarts, so an app that stops between steps 1 and 2 still opens with the
  old pair. `confirmPinChange` refuses with `invalidArgument`, changing nothing, unless the text
  it is given is the one the pending change returned, so confirming with the old text that an
  app still holds after such a stop cannot lock it out. It does nothing when no change is
  pending. A second `changePin` before confirmation keeps the pair it started from opening:
  from the old pair it replaces the pending key and the text of the first change stops opening;
  from the new pair, which the app stored, it makes that pair current and the old text stops
  opening. While a change is pending both pairs share the one failure count, and a wrong PIN
  costs two key derivations but counts as one failure.
- `EpicWallet.changePassword(currentPassword, newPassword)` changes the password of a wallet
  from `create` or `importWalletSeed`: the vault is encrypted anew under the new password
  (Argon2id, fresh salt). The current password attempt is counted and delayed as in `open`;
  a wrong one gives `wrongPassword` and changes nothing. A new password shorter than eight
  characters gives `invalidArgument`, and a PIN wallet `unsupported` (use `changePin`), both
  before any attempt is counted. LEPIC writes the new vault as `lepic.vault-next`, reads it
  back, writes it over `lepic.vault` and deletes `lepic.vault-next` last, so the store always
  holds a vault that opens: if the app stops part way, the old or the new password opens the
  wallet, and the next `open` with the one that works drops or finishes the change. This
  needs a `SecretStore` whose `write` has stored the value durably when its Future completes.
  `secretStore` means the store failed or did not give back what was written; the old password
  then still opens (or, if the store failed while replacing `lepic.vault`, either does until
  the next `open`). Forget any password the app remembered for the wallet after a change.
- `EpicWallet.importWalletSeed` and `EpicWallet.importWalletSeedWithPin` restore from the text of
  an `epic-wallet` `wallet.seed` (at most 4096 bytes) and its password, then work as `create` and
  `createWithPin` with a phrase: scan next. A wrong file password gives `wrongPassword`, text
  that is no `wallet.seed` `invalidArgument`. LEPIC keeps no copy of the file.
- `LepicRuntime.openLogRing(dir, maxBytes)` keeps every record at the runtime's log level,
  redacted, in at most `maxBytes` (4 KiB to 16 MiB) of files in `dir`, which should hold nothing
  else; `exportSupportBundle()` returns them as text for a feedback report. Only the values of
  the log vocabulary fields that say nothing about keys, amounts or addresses are kept, every
  other value becomes `[redacted]`. Messages are kept as they are, including the app's own lines
  from `logMessage`, so redact those before logging them.
- `EpicWallet.lock()` locks a wallet at once, for example when the app goes to the background:
  it stops the listener and any scan, wipes the keys and ends the calls still running, which
  fail with `cancelled` (a store write under way is finished first); every later call on that
  handle fails with `locked`. The wallet directory is released as soon as the database closes,
  at once when nothing was running, so the wallet can be opened anew on a fresh handle right
  away, before or after the old one is disposed. `dispose()` alone also locks, but only once
  calls still running on the handle finish, and releases the directory then.
- `deleteWallet` needs no password or PIN, so a user who forgot both can delete the wallet and
  restore it from the recovery phrase. Confirm with the user before calling it.
- A wallet directory is open in one runtime at a time, across processes too; LEPIC holds an OS
  lock on `.lepic.lock` in it while a wallet is open.
- `EpicWallet.events()` streams session, balance, transaction, sync and transport changes, and
  the invoice events `invoiceReceived`, `invoiceFinalized`, `invoiceExpired`, `invoicePosted`,
  `invoiceDeclined`, `invoiceWithdrawn` and `invoiceBounced`, which set `slateId`. A split or
  consolidation raises `selfSend` with the `txId` of its outgoing transaction, `account` and
  `amount`, never a `transaction` event with `to` `received`: nothing was received from
  anyone, and the listener stream reports nothing for it.
  `WalletEventKind` and `ListenerEventKind` only gain values, at the end, and a value never
  changes meaning; an exhaustive `switch` over either must handle the new ones.
  `TransactionDetails` has the required fields `flow` and `origin` (and `imported`, nullable)
  and `ListenerEvent` the required field `slateId`; code that builds them, such as a fake
  wallet, must pass them.
- `importLegacyHistory(sourceDir)` brings across the transaction history of the epic-wallet
  wallet (GUI or CLI) that a wallet was just made from, for example with `importWalletSeed`
  from that folder's `wallet.seed`. Call it once after the import, before or after the restore
  scan. Nothing in `sourceDir` is written. Imported transactions show `origin` `imported`
  with their original dates, types, fees, slate ids, messages and kernel, and `imported` gives
  the old wallet's id, its type and `check`, how the chain scan judged it. Outputs a scan found
  with no record show `origin` `foundByScan`, dated by their block. A history that cannot be
  imported is a `LegacyImport.status` (`noHistory`, `oldFormat`, `unreadable`, `sourceBusy`,
  `tooLarge`, `otherWallet`, `otherHistory`), not an error: the wallet keeps the scan's history.
- A slate received a second time, as text, as a file or through the listener, is not a second
  payment. `receiveSlate` and `receiveFile` return `ReceivedSlate.repeated` set, with the
  `txId` and the reply text of the first receive, and the listener reports kind `repeated`
  with that `txId` instead of `received`. Show it as already answered and hand out the same
  reply. `events()` reports nothing for a repeat. A relay copy of a message already answered
  and acknowledged reports nothing.
- The stream calls `refresh`, `scan`, `startListener`, `startHttpListener`, `startTor`, `events` and `logs` report a failure as
  the stream's error: the same `WalletError` the other calls throw, after which the stream ends.
  Listen with `onError`; no error from a stream call reaches the app's zone.
- A panic inside LEPIC arrives as `WalletError` with kind `panic`; the runtime stays usable.
  `RustLib.init()` installs a process-wide panic hook that prints only where a panic happened,
  never its message, so no text from inside LEPIC reaches the platform log.

## Native libraries

`hook/build.dart` adds the prebuilt `liblepic_ffi` for the target being built as a Flutter native
asset, so the app needs no Rust toolchain and no Gradle, Xcode or CMake changes. The library keeps the
flutter_rust_bridge stem `lepic_ffi`, so the generated `RustLib.init()` loads it the same way the
app loads its current `epic_wallet_core` library.

| Target | Library | Built on |
|---|---|---|
| Android arm64-v8a, armeabi-v7a, x86_64 | `native/<rust triple>/liblepic_ffi.so` | Linux or macOS, with the Android NDK and `cargo-ndk` |
| iOS device and simulator, arm64 | `native/<rust triple>/liblepic_ffi.dylib` | macOS with Xcode |
| Linux x86_64 | `native/x86_64-unknown-linux-gnu/liblepic_ffi.so` | Linux x86_64 |
| Windows x86_64 | `native/x86_64-pc-windows-msvc/lepic_ffi.dll` | Windows x86_64 with Visual Studio Build Tools (C++) |

Build them from the repository root before building the app:

```sh
cargo xtask mobile --package                       # every target this host can build
cargo xtask mobile --package --target aarch64-linux-android
```

The CI workflow `mobile.yml` builds the same libraries and uploads them as the artifacts
`lepic-ffi-android`, `lepic-ffi-linux` and `lepic-ffi-ios`. To use libraries kept elsewhere, for example unpacked
artifacts, set the directory in the app's `pubspec.yaml`:

```yaml
hooks:
  user_defines:
    lepic:
      native_dir: ../lepic-native # holds <rust triple>/liblepic_ffi.*
```

A relative `native_dir` is resolved against the directory of the app's `pubspec.yaml` (the
workspace root pubspec in a pub workspace), not against this package. Under it, each target needs
its own `<rust triple>/` directory, so flatten or rename CI artifact layouts to match.

- The libraries link against Android API 24; the hook fails for an app with a lower `minSdk`.
- They need no C++ runtime, so the app ships no `libc++_shared.so` for LEPIC.
- The Linux library links against the glibc of the machine that built it and does not load on
  an older one, so build it on the oldest distribution the app supports. A Linux app bundles it
  in `lib/` next to its executable.
- A missing library fails the app build with the `cargo xtask mobile` command that makes it.
- `cargo xtask mobile --package` writes a `SHA256SUMS` file next to each library, and the hook
  refuses a library that is not in it with that hash. Keep the file with the library when you
  move artifacts into a `native_dir`. It catches truncated, stale or mixed-up files; it is not a
  signature, so it does not stand in for trusting where the directory came from.
- The Windows library is built with MSVC and loads the Visual C++ runtime, as Flutter's Windows
  runner does. A Windows app bundles it next to its executable.
- macOS builds get no bundled library. `flutter test` on Linux gets the Linux
  library; see Develop.

To switch the app from its own Rust crate: depend on this package by path or git, delete the
app's `hook/build.dart` and `rust/`, and drop its direct `flutter_rust_bridge_hooks` and
`code_assets` dependencies unless something else uses them. `await RustLib.init()` stays. This is
not a drop-in swap: the app's imports of its own generated bindings
(`package:epic_wallet/src/rust/...`) change to `package:lepic/lepic.dart`, and its calls change to
the API in "Switching the app from its earlier binding" below.

## Secrets at the boundary

ADR 0014 decides what may cross. Every function in `crates/lepic-ffi/src/api` is checked against
this list.

| Direction | Value | Calls |
|---|---|---|
| Dart to Rust | Wallet password the user types | `EpicWallet.create`, `EpicWallet.open`, `EpicWallet.mnemonic`, `EpicWallet.importWalletSeed`, `EpicWallet.changePassword` (current and new) |
| Dart to Rust | PIN the user types | `EpicWallet.createWithPin`, `EpicWallet.openWithPin`, `EpicWallet.mnemonicWithPin`, `EpicWallet.importWalletSeedWithPin`, `EpicWallet.changePin` (old and new) |
| Dart to Rust | Password of an `epic-wallet` `wallet.seed` the user imports | `EpicWallet.importWalletSeed`, `EpicWallet.importWalletSeedWithPin` |
| Dart to Rust | Text of an `epic-wallet` `wallet.seed` the user imports (the encrypted seed) | `EpicWallet.importWalletSeed`, `EpicWallet.importWalletSeedWithPin` |
| Dart to Rust | Recovery phrase the user types, to restore or to check | `EpicWallet.create`, `EpicWallet.createWithPin` (`mnemonic`), `validateMnemonic` |
| Dart to Rust | Node API secret the user configures (`WalletConfig.node_api_secret`) | every call taking `WalletConfig`: `EpicWallet.create`, `open`, `createWithPin`, `openWithPin`, `importWalletSeed`, `importWalletSeedWithPin`, `nodeTip`; `deleteWallet` takes it and discards it |
| Dart to Rust | Recovery phrase of a test wallet, in `mock` builds only | `MockChain.fund` |
| Rust to the `SecretStore`, and back | PIN key (`lepic.pin-key`), random, one per PIN wallet | written by `EpicWallet.createWithPin` and `importWalletSeedWithPin`, replaced by `changePin`; read by `openWithPin`, `mnemonicWithPin` and `changePin`; deleted by `deleteWallet` |
| Rust to Dart | Recovery phrase, after the password or PIN is verified, for the backup screen | `EpicWallet.mnemonic`, `EpicWallet.mnemonicWithPin` |
| Never | Seed bytes, private keys, blinding factors, nonces, vault keys, the generated wallet password of PIN unlock, the root secret and the app data key derived from it | none |

Not secret, and crossing both ways: the sealed password text, the encrypted vault the
`SecretStore` holds, and the app's own data and the `.wfeh` files `sealAppData` and
`openAppData` make of it. Neither is enough alone. The vault needs the password. The sealed text needs
the PIN and the PIN key in the store, so whoever holds both the sealed text and the store's
contents can guess the PIN offline, slowed only by Argon2id. Keep the store on the device: back it
with the Android Keystore or the iOS Keychain (`ThisDeviceOnly`) and exclude it and the sealed text
from backups.

Every secret in the table crosses as a Dart `String`, in both directions. Rust copies what it
receives into memory it wipes, and wipes its own copies of what it returns, but it cannot wipe the
Dart string, nor the bridge's message buffer that carries the text across, which is freed without
being wiped. A Dart string stays in memory until the garbage collector reuses it. Hold these
strings only as long as the call needs them: pass a typed password, PIN or phrase straight from the
text field to the call and clear the field afterwards, and keep the phrase from `mnemonic` on
screen only as long as needed, without copying it into other state.

## Errors

`WalletError.kind` is a `WalletErrorKind`; `WalletError.code` is its number. Codes never change
meaning. `message` is English for logs and bug reports and holds no secret; do not parse it.

| Code | Kind | Meaning |
|---|---|---|
| 1 | `invalidMnemonic` | The recovery phrase is not valid BIP-39 English. |
| 2 | `wrongPassword` | The password or PIN did not open the vault or sealed text. |
| 3 | `walletAlreadyExists` | The secret store already holds a wallet. |
| 4 | `walletNotFound` | The secret store holds no wallet. |
| 5 | `nodeUnreachable` | The node failed, refused, answered badly, or is behind the wallet. |
| 6 | `notEnoughFunds` | Not enough spendable funds for the amount and fee. |
| 7 | `invalidSlate` | The slate is malformed, of the wrong stage, already handled, or does not verify. |
| 8 | `invalidArgument` | An argument or configuration value was rejected. |
| 9 | `transportFailed` | The Epicbox relay or the slate file failed. |
| 10 | `chainBusy` | Never returned; kept so code written for the earlier binding compiles. |
| 11 | `walletBusy` | A wallet on this directory is already open, in this runtime or another one or another process. |
| 12 | `paymentExpired` | The slate's time to live passed. Nothing was signed or posted. |
| 13 | `io` | The wallet database or a file could not be used. |
| 14 | `other` | Anything else. |
| 15 | `locked` | The wallet handle is locked. |
| 16 | `foreignWallet` | The directory holds another wallet's or another network's database. |
| 17 | `secretStore` | The app's secret store failed or holds a damaged vault. |
| 18 | `notPosted` | Finalized and stored, but the node did not accept it. Repost it. |
| 19 | `cancelled` | The operation was cancelled, for example `cancelScan`. |
| 20 | `unsupported` | Not available in this build or configuration, for example Epicbox without a relay. |
| 21 | `panic` | A defect inside LEPIC. The operation was abandoned. |
| 22 | `restoreScanRequired` | The wallet was restored from its phrase and no full scan has completed since, so it cannot receive or make change yet. Run `scan` to the end first. |
| 23 | `changedDuringCancel` | Another operation, such as the listener finalizing it, changed the transaction while it was being cancelled. Nothing was cancelled; cancel again to decide from the new state. |
| 24 | `onChain` | The node already holds the transaction's kernel, so it cannot be cancelled or released. The next refresh confirms it. |
| 25 | `foreignAppData` | The app data file is intact but belongs to a wallet with another seed. |
| 26 | `damagedAppData` | The app data file belongs to this wallet but was changed or cut short. |
| 27 | `inPool` | The node's transaction pool holds the transaction, so it may still be mined and is not cancelled or released. Refresh later. |
| 28 | `notReleasable` | `release_transaction` refused: the transaction is not a finalized or posted send, or `releasable` is still false. |
| 29 | `invoiceNotFound` | No invoice with that slate id waits to be paid or declined: it was paid, declined, deleted by a sweep, or never arrived. |
| 30 | `amountMismatch` | The invoice asks for another amount than the one the user typed. Nothing was paid. |
| 31 | `notDelivered` | The invoice or its payment is stored, but the relay did not take it. Deliver a payment again with `resendInvoicePayment`, or cancel either with `cancelTransaction`. |
| 37 | `damagedDatabase` | The wallet database was damaged. LEPIC renamed it, with its log files, to `wallet.sqlite3.damaged-<unix seconds>` in the data directory and kept it. Open the wallet again: the database is rebuilt from the vault as after a restore, so run `scan` to the end before sending or receiving. History, labels and messages are not in the new database. |
| 40 | `httpUrlInvalid` | The address given to `sendHttp` or `resendHttp` is not an `http(s)://host[:port][/path]` URL, or names a `.onion` host. Nothing was stored. |
| 41 | `plainHttpNotAllowed` | The address uses plain `http` to another computer and `allowPlainHttp` was false. Nothing was stored. Ask the user, or use `https`. |
| 42 | `onionAddressInvalid` | The address given to `sendTor` or `resendTor` is not an onion v3 address, or has a typo. Nothing was stored. |
| 43 | `torNotRunning` | The wallet's tor is not running or not yet bootstrapped. Before the send nothing was stored; when tor stopped during the delivery the send is stored as `sent`. |
| 44 | `onionUnreachable` | The other wallet is not online with Tor on, or was not reached in time. The send is stored as `sent` with its inputs locked: resend it later or cancel it. |
| 45 | `changeTooSmall` | The change has fewer base units than the change outputs asked for in `SendOptions`. Nothing was stored; ask for fewer change outputs. |
| 46 | `tooHeavy` | The send would spend more inputs or make more outputs than a transaction may hold. Nothing was stored; send less, or consolidate first. |
| 47 | `nothingToConsolidate` | `consolidateOutputs` found fewer than two spendable outputs, so there is nothing to merge. Nothing was stored. |

Kinds 22 to 24 used to arrive as `other`. Kinds 25 and 26 are new with `sealAppData` and
`openAppData`, 27 and 28 with `releaseTransaction`, 29 to 31 with the invoice calls, 40 and
41 with the HTTP calls, 42 to 44 with the Tor calls, 45 and 46 with `SendOptions` (before, both
arrived as `invalidArgument`), 47 with `consolidateOutputs` (before, `notEnoughFunds` or a
consolidation of one output). An exhaustive `switch` over `WalletErrorKind` must handle them.

## Direct transactions over HTTP

A wallet that runs `epic-wallet listen -m http`, or another LEPIC wallet's HTTP listener, answers
a send in the same exchange, so `sendHttp` creates the send, delivers it, finalizes the answer and
posts the transaction in one call (ADR 0017):

```dart
final sent = await wallet.sendHttp(
  amount: BigInt.from(150000000),
  minimumConfirmations: BigInt.from(3), // what the summary counts as spendable
  url: 'https://wallet.example.org',
  allowPlainHttp: false,
);
if (!sent.posted) await wallet.repostTransaction(txId: sent.txId);
```

- A missing port is 3415 for `http` and 443 for `https`; `/v2/foreign` is appended. Plain `http`
  goes only to this device unless `allowPlainHttp` is true: set it only after the user agreed
  that the slate travels unencrypted. Otherwise the call throws `plainHttpNotAllowed`.
- When the other wallet cannot be reached or refuses, `sendHttp` throws `transportFailed` and the
  send stays stored as `sent` with its inputs locked. Deliver it again with
  `resendHttp(txId, url, allowPlainHttp)`, to the same or another address, or cancel it. A
  wallet that answered the slate before answers it again the same way, so a resend after a lost
  answer is safe.
- `posted` is false when the transaction was finalized but the node refused it; repost it.

The wallet's own listener answers payments only, never invoices, and never starts by itself:

```dart
wallet.startHttpListener(exposure: HttpExposure.localOnly, port: 3415).listen((event) {
  switch (event.kind) {
    case HttpListenerEventKind.started: // event.port, event.exposure
    case HttpListenerEventKind.received: // event.txId, event.amount, event.repeated
    case HttpListenerEventKind.portInUse: // pick another port
    default:
  }
});
```

- `localOnly` listens on `127.0.0.1`; `internet` on every interface, for a port the user forwards
  from the router. Anyone who reaches the port can send the wallet payments, so offer `internet`
  only on the user's explicit choice. Port 0 lets the system pick one.
- The first event is `started`, `portInUse` or `bindFailed`; after a start the last one is
  `stopped`, once the port is free. `refused` carries `HttpRefusal.rejected` for a slate refused
  for good and `unavailable` when the wallet cannot take payments now, for example while its
  node is unreachable. Events never name the sender or its address.
- One listener runs per wallet: a second `startHttpListener` gets a stream that ends at once.
  `stopHttpListener`, `lock` and dropping the wallet stop it; `httpListenerStatus()` returns the
  running listener's port and exposure, or null. On a locked wallet the stream ends with
  `locked` as its error.
- Each request may take up to a minute. At most 16 connections are served at once, further ones
  are closed, and payments beyond 30 a minute are refused to the sender as `unavailable`.

## Direct transactions over Tor

On desktop and Android the wallet runs its own tor, from a `tor` binary the app bundles (the
Tor Expert Bundle; on Android its `libTor.so`, shipped as the native library `libtor.so`), and
receives at its onion: its payment-proof address in onion form, the address
`epic-wallet address` prints, which survives a restore from the phrase (ADR 0018). iOS cannot
run the binary: there `startTor` starts nothing, and its stream gets `failed` with
`TorFailureKind.missing`, then `stopped`. Tor is off until the app starts it, per wallet:

```dart
final onion = await wallet.onionAddress(); // known before tor runs
wallet.startTor(torBinary: torPath, libDir: torLibDir).listen((event) {
  switch (event.kind) {
    case TorEventKind.starting: // event.progress, 0 to 100
    case TorEventKind.bootstrapped: // sends work
    case TorEventKind.ready: // event.onion: others can pay this wallet
    case TorEventKind.failed: // event.failure
    case TorEventKind.received: // event.txId, event.amount, event.repeated
    case TorEventKind.stopped: // the last event
    default:
  }
});
final sent = await wallet.sendTor(
  amount: BigInt.from(150000000),
  minimumConfirmations: BigInt.from(3), // what the summary counts as spendable
  onion: 'http://<56 characters>.onion',
  // options: SendOptions(...) chooses the inputs and change, as for sendHttp.
);
```

- `libDir` goes on the library path for the libraries the bundle ships on Linux; pass null on
  Windows and Android. On Android pass `<nativeLibraryDir>/libtor.so` as `torBinary`: the
  native library folder is the one place an app may run a file from. Tor keeps its files in `tor/` inside the wallet's data directory, never shared
  between wallets. Check the bundle's hashes before passing its path.
- While tor runs, the wallet listens on `127.0.0.1` on a port of its own, separate from
  `startHttpListener`, and tor forwards the onion's port 80 there. Its payments arrive on the
  tor stream as `received` and `refused`, as on the HTTP listener's stream, and are recorded with
  transport `tor`, with open receipts capped apart from those over HTTP. Tor connects every
  sender to that listener from `127.0.0.1`, so the listener does not limit connections per
  address; tor closes a sender's circuit that opens more than 4 connections at once.
- The events go `starting`, `bootstrapped`, `publishing`, `ready`. `failed` with
  `TorFailureKind.listener` or `keys` leaves tor running for sends, and `torStatus()` stays
  `bootstrapped` with that `failure`; any other failure is followed by `stopped`. `missing`
  means no binary at the path, `network` no progress connecting, `clock` a wrong system clock.
  Restarting is the app's choice: call `startTor` again after `stopped`. A tor that an earlier
  run of the app left on the wallet's files (the app was killed) is halted by the next
  `startTor`, and the onion is the same on every start.
- Call `refreshTor(networkChanged: false)` when the app comes back to the foreground and
  `refreshTor(networkChanged: true)` when the device's network changed or came back. Tor
  leaves its dormant state; after a network change it drops every connection and builds new
  ones, so sends in progress fail and tor republishes the onion by itself (no new `ready`). It
  throws `torNotRunning` when no tor runs (start one) and `locked` on a locked wallet; a tor
  that does not answer is ended, the call throws `torNotRunning` and the stream gets `failed`
  then `stopped`. Time a paused app spent frozen (Android's cached-app freezer) does not count
  against tor's bootstrap and publish limits.
- One tor runs per wallet: a second `startTor` gets a stream that ends at once. `stopTor`, `lock`
  and dropping the wallet stop tor, then its listener; the stream then ends with `stopped`.
  A `startTor` right after `stopTor` or `lock` waits for the tor stopped last to be down, as
  both use the same files, and fails with `start`, then `stopped`, when that takes over 30
  seconds. `torStatus()` reports `off`, `starting`, `bootstrapped`, `publishing` or `ready`.
- `sendTor` needs `bootstrapped` or later, else it throws `torNotRunning` and stores nothing.
  It reads the address as `validateOnionAddress` does: with or without `.onion`, `http://`, a
  port or a path, which are dropped. Once the wallet has checked it can pay the amount and its
  fee, it puts `sending` on the tor stream: reaching an onion that
  is not online takes up to about 150 seconds before it throws `onionUnreachable`, so show
  progress. The result is the `HttpSentTx` of `sendHttp`. A send that throws
  `onionUnreachable`, `torNotRunning` after it started, or `transportFailed` is stored as `sent`:
  deliver it again with `resendTor(txId, onion)` or `resendHttp`, or cancel it.

## Invoices over Epicbox

A service issues an invoice, the user pays it with one call, and the service finalizes and
posts it, so a user on a weak connection answers only once. Invoices travel between LEPIC
wallets; a stock `epic-wallet` sends an invoice back unpaid.

Payer, the app:

- `invoiceAddress()` is the address to give to services, at address index 1 or higher beside the
  payments address of `epicboxAddress()`. `rotateInvoiceAddress()` moves to the next index and
  abandons the old address. A restore from the phrase starts at index 1 again; keep
  `invoiceAddressIndex()` and give it back with `setInvoiceAddressIndex(index)`.
- The invoice address hears only from allowed senders: `allowInvoiceSender(address, label)` with
  the full `<key>@<relay>[:port]` the service shows, `invoiceSenders()`, `removeInvoiceSender`.
  Only the key is matched, and payments go to the address as added.
- `drainInvoices()` reads the invoice address once, as `drainEpicbox()` reads the payments
  address; no listener runs on it. Messages from other senders are dropped unopened and counted
  in `InvoiceReport.dropped`. Each new invoice raises an `invoiceReceived` event.
- `pendingInvoices(expirySecs)` lists what waits: slate id, sender address, amount, the sender's
  message cleaned for display, and when it was received and expires. Nothing in the inbox ever
  pays.
- `payInvoice(slateId, amount, minimumConfirmations, message)` pays only when `amount` is the
  invoiced amount (`amountMismatch` otherwise) and delivers the payment to the sender. On
  `notDelivered` the payment is stored with its inputs locked: `resendInvoicePayment(txId)` with
  the `txId` of the transaction whose `slateId` is the invoice's, or `cancelTransaction(txId)`.
- `declineInvoice(slateId)` refuses it for good and tells the sender.

Issuer, a service wallet:

- `issueInvoiceEpicbox(amount, address, message)` sends the invoice to the payer's invoice
  address. Its transaction is `incoming` like a received payment, with `flow` `invoice`; a
  paid invoice is `outgoing` with `flow` `invoice`. The payment arrives on the payments
  address, where `drainEpicbox()` or the listener finalizes and posts it with an
  `invoiceFinalized` event. `cancelTransaction` withdraws an unpaid invoice. A payer that does not pay invoices, such as a stock `epic-wallet`, sends the
  invoice back; `drainEpicbox()` counts it in `InboxReport.bounced`, and that payer is never
  sent a notice. Each bounced invoice raises one `invoiceBounced` event with its `txId` and
  `slateId`, on `events()` and, while it runs, the listener's stream (`ListenerEvent.slateId`).
  If the app stops before the relay message is settled, the redelivered bounce raises it again
  for the same `txId`; treat a repeat as the same bounce.
  Cancel the invoice, or send that payer a slate file.
- `peerCapability(address)` says what this wallet learned about a payer from its own
  messages, matched on the key: `unknown` before any contact, `noInvoices` once it sent an
  invoice back, `lepic` once a payment or notice from it proved it runs LEPIC. Warn before
  invoicing a `noInvoices` payer. It reads only the wallet database and needs no relay.

Notices tell each side what the other did: the issuer sends `posted`, with the kernel excess,
after it posts a payment and `withdrawn` when it cancels an invoice; the payer sends `declined`.
They arrive with `drainInvoices()` (`posted`, `withdrawn`) and `drainEpicbox()` or the listener
(`declined`), are counted in `notices`, and raise the events `invoicePosted` (`txId` of the
payment, `slateId`, `kernelExcess`), `invoiceWithdrawn` and `invoiceDeclined`. They are advisory
and never move funds: `withdrawn` deletes a waiting invoice, and for one already paid names the
payment in `txId` so the app can offer `cancelTransaction`. A notice goes only to a wallet that
proved it runs LEPIC in an earlier exchange, so the first invoice to a new payer is withdrawn
silently, and a stock `epic-wallet` is never sent one.

Both sides run `sweepInvoices(expirySecs)` from time to time. Unpaid invoices expire after
`expirySecs`, a day by default and at most two days: waiting and declined ones are deleted,
issued ones cancelled, each with an `invoiceExpired` event. A payment whose time to live passed
with the transaction neither on chain nor in the node's pool is listed in
`InvoiceSweep.cancellable`; offer the user `cancelTransaction`. Pass the same `expirySecs` to
`pendingInvoices` and `sweepInvoices`.

## Switching the app from its earlier binding

The app's earlier Rust API (`app/rust/src/api`, over `epic-wallet`) maps to this package as
below. Calls on a wallet are methods of `EpicWallet` in both. "New" arguments are the runtime and
the secret store, which the earlier binding kept in process-wide state.

| Earlier call | LEPIC call | Change |
|---|---|---|
| `init_app` (frb init) | none | Nothing global is installed. `RustLib.init()` stays. |
| `generate_mnemonic(word_count)` | not provided (ADR 0014) | `EpicWallet::create` without `mnemonic` generates the seed; show it with `mnemonic(password)`. |
| `validate_mnemonic(phrase)` | `validate_mnemonic(phrase)` | Same. |
| `wallet_exists(config)` | `wallet_exists(runtime, store)` | Asks the secret store, not the directory. |
| `inspect_slate(json)` | `inspect_slate(json, chain)` | Free function, no wallet. Reads the text as `receive_slate` does and returns `SlateInfo`: version, stage, amount, fee, TTL, slate id and messages. Signatures are not checked. |
| `validate_epicbox_address(address)` | `validate_epicbox_address(address, chain)` | Chain is explicit, and the `@<relay>` part is required: a bare key is refused. |
| `delete_wallet(config)` | `delete_wallet(runtime, config, store)` | Fails with `walletBusy` at once instead of waiting 20 s. Also deletes the vault. |
| `node_tip(config)` | `node_tip(runtime, config)` | Same result. |
| `EpicWallet::create(config, mnemonic, password)` | `EpicWallet::create(runtime, config, store, mnemonic, password)`, or `EpicWallet::create_with_pin(runtime, config, store, mnemonic, pin) -> PinWallet` | Same semantics. The PIN form returns the wallet and `sealed_password`. |
| `EpicWallet::open(config, password)` | `EpicWallet::open(runtime, config, store, password)`, or `EpicWallet::open_with_pin(runtime, config, store, pin, sealed_password)` | Same. |
| `mnemonic(password)` | `mnemonic(password)`, or `mnemonic_with_pin(pin, sealed_password)` | Same check against the stored vault. |
| `summary(refresh, minimum_confirmations)` | `summary(refresh)` | Balances count an output spendable after 3 confirmations, as the Epic GUI wallet does (`epic-wallet info` counts 10); `WalletSummary.minimumConfirmations` carries the number, so sends and estimates can pass it. `refresh: false` answers from the store without the node, also on a handle that never refreshed. |
| `refresh(minimum_confirmations, progress)` | `refresh()` stream | First event 0 %, last 100 % with `summary`. |
| `scan(start_height, progress)` | `scan(start_height)` stream | `ScanProgress` adds `height` and `target_height`. New: `cancel_scan()`. |
| `transactions(refresh)` | `transactions()`, `transaction(tx_id)` | From the store alone, newest first; refresh first with `summary(refresh: true)`. `TransactionDetails` carries the slate id, kernel excess, confirmed height and time, counterparty, amounts, fee, status, creation time and TTL cutoff, and for a finalized or posted send whether and from which height it can be released. `messages` lists each party's message whose signature verifies, as a `SlateMessage` with `role` (`sender` or `receiver` of the money) and `text`, from the latest stage the wallet stored: a send shows its own, a receive the sender's and its own, a finalized send both. A transaction restored by a scan has none. `flow` is `payment` or `invoice`, from the slate stages stored: with `direction`, an incoming payment was received and an outgoing one sent, an incoming invoice was issued by this wallet and an outgoing one paid by it. |
| `enrich_history()` | not provided | App history archive; not an engine feature. |
| `set_tx_note(key, note)` | not provided | App history archive; not an engine feature. |
| `contacts()`, `save_contact`, `delete_contact` | not provided | App address book; keep it in Dart. |
| `export_history()`, `import_history(data)` | `seal_app_data(payload)`, `open_app_data(file)` | The `.wfeh` envelope only: Dart builds and parses the payload JSON. Files of the earlier binding open, since the key comes from the same root secret (`docs/compat/wfeh.md`). Another wallet's file gives `foreignAppData`, a changed one `damagedAppData`, a later version `unsupported`. |
| `export_history_csv()` | not provided | App history archive; not an engine feature. |
| `estimate_max(minimum_confirmations)` | `estimate_max(minimum_confirmations)` | Returns `FeeEstimate`. A send of that amount at the same tip charges that fee. |
| `estimate_fee(amount, minimum_confirmations)` | `estimate_fee(amount, minimum_confirmations)` | Returns `FeeEstimate` with the inputs and change too. The sends choose inputs the same way, so the fee matches. |
| `epicbox_address()` | `epicbox_address()` | `unsupported` when no relay is configured. |
| `create_send_slate(amount, minimum_confirmations)` | `create_send_slate(amount, minimum_confirmations, message)` | `Slate` adds `tx_id`. New file form: `send_file(amount, minimum_confirmations, path, message)`. The optional `message` is signed into the slate, as `epic-wallet send --message` does, after it is cut to its first 256 bytes on a character boundary. |
| `receive_slate(slate_json)` | `receive_slate(slate_json)` | Returns `ReceivedSlate`: the fields of `Slate` plus `repeated`. A slate received before returns the answer stored then, with `repeated` set and the first call's `tx_id`; nothing is stored or signed again. New file form: `receive_file(path)`, writes `<path>.response`, for a repeat too. |
| `finalize_and_post(slate_json)` | `finalize_and_post(slate_json)` | Returns `FinalizedTx`; a refused post fails with `notPosted`. New: `finalize_file(path)`. |
| `send_http(amount, minimum_confirmations, url)` | `send_http(amount, minimum_confirmations, url, allow_plain_http, message)` | Returns `HttpSentTx`, finalized and posted. Over Tor: `send_tor(amount, minimum_confirmations, onion, message, options)` after `start_tor`. Both take the optional `SendOptions` of `create_send_slate`. |
| `send_epicbox(amount, minimum_confirmations, address)` | `send_epicbox(amount, minimum_confirmations, address, message)` | Returns `SentTx`. `message` as for `create_send_slate`. Like `validate_epicbox_address`, refuses a bare key without `@<relay>` with `invalidArgument` and stores nothing. |
| `start_listener(events)` | `start_listener()` stream | Kinds `connected`, `disconnected`, `received`, `repeated`, `finalized`, `error`, `stopped`, `invoiceBounced`. `repeated` carries the `tx_id` of a payment answered before whose slate arrived again; `invoiceBounced` the `tx_id` and `slate_id` of an issued invoice the payer sent back. New: `drain_epicbox()` for background work. |
| `stop_listener()` | `stop_listener()` | Same. |
| `listener_running()` | `listener_running()` | Same. |
| `repost_transaction(key)` | `repost_transaction(tx_id)` | Local transaction id instead of the history key. |
| `release_stuck_send(key)` | `release_transaction(tx_id)` | `TransactionDetails.releasable` replaces `TxEntry.releasable`, and `releasable_from` gives the height a refresh must reach first: 1440 blocks after finalizing, as before. Unlike the earlier rule, a posted send the node dropped and a finalized one whose post got no answer are released too; a kernel still missing a day of blocks later means the same in each case. The node is asked once more: `onChain` or `inPool` when it holds the transaction, `nodeUnreachable` when it cannot be asked. If another node mines the transaction later, a new send that spends the same inputs fails. A refresh within 10080 blocks, about a week, of the release finds the kernel: the transaction moves from `cancelled` to `confirmed`, with an event, and its change returns to the balance. One mined later keeps showing `cancelled`, and its change returns only after a `scan`. |
| `cancel_transaction(tx_id)` | `cancel_transaction(tx_id)` | A finalized transaction is refused with `onChain` or `inPool` while the node's chain or pool holds its kernel. |
| `refresh_with`, `scan_with`, `start_listener_with`, `*_for_tests` | none | Rust-only hooks of the earlier binding. Tests use `MockChain`. |
| `init_logging(dir)` | `LepicRuntime::open_log_ring(dir, max_bytes)`, and the `LepicRuntime::logs()` stream | The ring keeps redacted records within `max_bytes`; it does not return a file path. |
| `log_message(level, tag, message)` | `LepicRuntime::log_message(level, tag, message)` | Target `dart`, tag as a field. |
| `read_log_tail(max_bytes)` | `LepicRuntime::export_support_bundle()` | The whole ring, redacted, with a short header. |
| `redact_text(text)` | not provided | The ring redacts by field, not free text; redact the app's own text in Dart. |
| `generate_wallet_password()` | not provided (ADR 0014) | `create_with_pin` generates the password inside Rust. |
| `seal_password(pin, password)` | not provided (ADR 0014) | `create_with_pin` returns the sealed text. Text sealed by the earlier binding does not open here; users moving from the earlier core restore from their phrase or their `wallet.seed` anyway, LEPIC imports an `epic-wallet` wallet's history but never its keys, and get new sealed text from `create_with_pin` or `import_wallet_seed_with_pin`. |
| `open_password(pin, sealed)` | not provided (ADR 0014) | `open_with_pin(.., pin, sealed_password)` opens the wallet; wrong PIN gives `wrongPassword`, damaged text `invalidArgument`. |

Types: `WalletConfig` keeps its fields; `Chain` has no `usernet`. `WalletError` and
`WalletErrorKind` keep their names and earlier kinds, plus the new ones above. `TxEntry`
becomes `TransactionDetails`. `FeeEstimate` and `SlateInfo` keep their names and gain fields;
`SlateInfo.stage` is a `SlateStage` from `s1` to `i3`. `Contact` and `ImportReport` have no
counterpart.

## Develop

Regenerate the bindings after changing `crates/lepic-ffi/src/api`, with the codegen at the
version pinned in the root `Cargo.toml`:

```sh
cd bindings/flutter
dart run tool/generate.dart
```

It runs `flutter_rust_bridge_codegen generate` and then makes every stream decode its errors as
`WalletError`, since the codegen always decodes stream errors as `AnyhowException`. Running the
codegen alone leaves stream errors undecodable, which the stream tests in `test/wallet_test.dart`
catch. On Linux `dart run` also runs this package's build hook, which needs the host library in
`test_native/`; run `cargo xtask mobile --host-test` (below) once first.

Run the tests on x86_64 Linux, from the repository root:

```sh
cargo xtask mobile --host-test
```

It builds `lepic-ffi` with the scripted node (`mock` feature) for the host, writes it to
`test_native/`, which this package's `pubspec.yaml` names as `native_dir`, and runs
`flutter test` here. The build hook bundles the library from there, as it would for a Linux app,
and the tests open the copy it installed. After a Rust change, run the command again; for Dart
changes alone `flutter test` is enough. `MockChain` works only in a `mock` build; in any other
build it fails with `unsupported`. So does `MockRelay`: with
`MockChain.runtimeWithRelay(logLevel, relay)` every Epicbox connection of the runtime's wallets
goes to it, whatever relay they are configured with. `MockStockPeer` is a peer on that relay
that sends every message back as a stock `epic-wallet` does with an invoice, and can post any
text.

`emulator_test/` is an app with no UI whose integration test loads the bundled library on an
Android device and runs create, restore, file send, receive and finalize against `MockChain`.
With an emulator or device attached (`adb devices`), from the repository root:

```sh
cargo xtask mobile --emulator-test                 # the only attached device
cargo xtask mobile --emulator-test --device emulator-5554
```

It builds `lepic-ffi` in release with the `mock` feature for the device's ABI, writes it to
`emulator_test/native/`, which the app's `pubspec.yaml` names as `native_dir`, and runs
`flutter test integration_test` there. `adb` and `flutter` come from `$ANDROID_HOME` and
`$FLUTTER_ROOT` when set, otherwise from `PATH`. A headless emulator for it, from an installed
system image; `-read-only` leaves the AVD unchanged, so several runs can share it:

```sh
avdmanager create avd -n lepic_test -k "system-images;android-36;google_apis;x86_64" -d pixel_6
emulator -avd lepic_test -read-only -no-window -no-audio -no-boot-anim -no-snapshot &
adb wait-for-device shell 'while [ "$(getprop sys.boot_completed)" != 1 ]; do sleep 2; done'
```

## Test against a local chain

`interop/acceptance` runs a reference node `v4.0.4` on a usernet chain, an Epicbox relay, a miner
and an `epic-wallet` `v4.0.2` funder in Docker, on 127.0.0.1 only, with no public service
involved. The app and the tests below use it with `Chain.mainnet`, because `epic-wallet` derives
mainnet Epicbox addresses on usernet; there is no separate `Chain` value. Needs Docker with
Compose, `jq`, `curl` and `flock`; `interop/README.md` lists the rest. From the repository root:

```sh
interop/acceptance/run.sh --stack-only    # builds once, starts a clean chain, Ctrl-C to stop
```

It prints the settings for `WalletConfig` and keeps the stack, and the lock that stops a second
run on this host, until it is stopped; stopping removes the chain and the wallets.
`interop/acceptance/chain.sh` drives the running stack:

| Command | Does |
|---|---|
| `chain.sh env` | prints `LEPIC_INTEROP_NODE_URL`, `LEPIC_INTEROP_NODE_API_SECRET_FILE`, `LEPIC_INTEROP_EPICBOX_DOMAIN`, `LEPIC_INTEROP_EPICBOX_PORT` and `LEPIC_INTEROP_EXCHANGE_DIR` |
| `chain.sh height` | the node's tip height |
| `chain.sh mine <blocks>` | waits until that many more blocks are mined; the miner adds one every few seconds |
| `chain.sh fund <address> <epic>` | the funder sends that amount to an Epicbox address; the wallet answers it with `drainEpicbox()` or its listener, and the funder finalizes and posts |
| `chain.sh receive <file>` | the funder answers a send file the wallet wrote into the exchange directory, writing `<file>.response` for `finalizeFile` |

A wallet on this chain uses the printed values: `nodeUrl` http://127.0.0.1:43413, `nodeApiSecret`
the contents of the secret file, `epicboxDomain` `localhost` and `epicboxPort` 3423. Funds become
spendable after 3 confirmations, well under a minute. The funder's first coinbase matures a few blocks
after the chain starts, so `fund` waits for it.

`test/interop_test.dart` does this end to end: it creates a wallet, is funded 10 EPIC by the
funder over Epicbox, refreshes until the funds are spendable, sends 2 EPIC back by file and waits
until the change is spendable. It is skipped unless `LEPIC_INTEROP=1`. With the stack running,
from the repository root (the first command fills `test_native/`, see Develop):

```sh
cargo xtask mobile --host-test
cd bindings/flutter && LEPIC_INTEROP=1 flutter test test/interop_test.dart
```
